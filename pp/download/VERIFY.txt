Famspace unlock - install checklist
====================================

The XAPK is stored uncompressed and laid out exactly like the one from the
Play Store (base APK first, manifest.json last) - some XAPK installers read
the entries straight out of the archive and refuse a compressed one.

Install (simplest):
  1. uninstall the current Famspace completely (long-press -> uninstall, or
     "adb uninstall com.famspace.app.android") - a half-updated install can
     keep the old proxy code
  2. delete the previously downloaded APK/XAPK from the phone
  3. install Famspace-universal.apk (one file, no XAPK installer, no splits)
     or FamSpace-unlocked.xapk with an XAPK installer
  4. OPEN THE APP and leave it in the foreground for a moment

  The rewrite proxy runs INSIDE the app process, so nothing listens on
  127.0.0.1 until the app is running. Open the app first, then the log URL.

Checking the build and the wallet
---------------------------------
Open this in the phone's browser (while the app is running):

     http://127.0.0.1:8888/__famunlock/log
     http://127.0.0.1:8888/__famunlock/health

The FIRST line of the log page is always a banner:

     FamUnlock proxy build 2026-11-27-wallet8  listening on ports 8888,888
     [rewritten: <n>, repair: <state>]

  * banner present  -> this is the current build
  * "rewritten: 0"  -> no encrypted answer has been rewritten yet; open the
                        "me" page of the app, that is what asks for the
                        profile
  * no banner       -> an OLD build is still installed

8888 is the port the app talks to. 888 is the legacy port and only binds on
devices that allow privileged ports, so on a normal phone use 8888.


The wallet is rewritten inside the encrypted payload
----------------------------------------------------
The API does not answer with plain JSON.  Every answer is

     {"success":true,"code":200,"responseData":"<encrypted, base64>","t":…}

so the wallet lives inside an ENCRYPTED payload and rewriting it by field
name alone can never reach it.  The proxy

  1. decrypts the payload (AES-128-CBC, the key is picked by the index byte
     at the end of the blob, the IV is the key itself),
  2. rewrites the wallet (coins/gems -> 999999999, vipLv -> 99, vipEnd ->
     2147483647, canView -> true, costs -> 0, ...),
  3. encrypts it again with the same key and the same index byte, so the app
     decrypts it exactly as it would the original.

In the log:

  "decrypted responseData: {...}"
      what the server really sent
  "wallet: coins=999999999, gems=999999999, vipLv=99, vipEnd=2147483647"
      what the app is going to see - THIS is the line to look for
  "decrypted rewrite: [coins, gems, vipEnd, vipLv]"
      what the proxy changed inside the encrypted payload
  "re-encrypted responseData (289 bytes)"
      the answer was encrypted again and sent to the app
  "responseData is encrypted with an unknown key (index 'x')"
      the index byte named a key that is not in the table - the answer is
      passed through untouched

The "repair" field is the one-time fix of the store the previous build
damaged.  That build rewrote the app's MMKV file as if it were text; MMKV
records are length-prefixed, so the rewrite shifted every record after the
first one and the stored access token became unreadable ("ccess_token" +
varint bytes + the JWT).  Dio then rejected the header with "Invalid HTTP
header field value" and every page that needs the token failed.  A shifted
MMKV file cannot be repaired, so this build removes it once, before the
Flutter engine opens it:

  "repair: cleared MMKV - log in again"
      the MMKV store contained the corruption signature from the previous
      build; the app now asks for the login. This happens exactly once.
  "repair: store ok" / "repair: done earlier"
      no corruption was found, or the one-time check already ran.

The proxy never writes to the app's storage any more - the wallet is
rewritten inside the encrypted answer, which is the copy the app uses.

Every request (with its headers) and every answer (with its body) is in the
log, so nothing has to be guessed.

If it refuses to install, adb prints the exact reason:
  INSTALL_FAILED_INVALID          -> a .so was compressed (wrong file)
  INSTALL_FAILED_UPDATE_INCOMPATIBLE -> the Play version is still installed
  INSTALL_FAILED_MISSING_SPLIT    -> the splits were not installed together

What this still cannot do
--------------------------
The unlock call is checked SERVER-SIDE
(POST /api/v1/space/favorite/unlock -> {"code":402,"error":"insufficient
coins"}).  The rewrite makes the CLIENT believe it is a member; whether a
paid space really opens depends on whether the server hands out the playUrl.
